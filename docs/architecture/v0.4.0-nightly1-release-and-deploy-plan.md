# NEXUS v0.4.0-nightly.1 — Auditoria de Compatibilidade, Plano de Deploy e Rollback

**Branch:** `feat/v0.4.0-phase-a-foundation`  
**Escopo:** Auditoria pré-deploy do backend `nexus-server` (`v0.4.0` vs `v0.2.5 Stable`), preservação de dados do cliente desktop na futura atualização `v0.2.5 Stable -> v0.4.0 Stable`, plano de backup e rollback na AWS e governança estrita de canais (`Nightly -> Homologação -> Stable`).

## 1. Prova Técnica de Compatibilidade do Backend (`v0.4.0` vs `v0.2.5 Stable`)

### 1.1 Migrações `20261112000007..009` são estritamente aditivas

A inspeção direta das três novas migrações da fase `v0.4.0` confirma que nenhuma tabela, coluna, constraint ou índice existente na `v0.2.5` é alterado, renomeado ou removido:

| Migração | Comandos DDL executados | Tabelas criadas | Impacto em tabelas `v0.2.5` |
| --- | --- | --- | --- |
| `nexus-server/migrations/20261112000007_communities_core.sql` | Apenas `CREATE TABLE IF NOT EXISTS` e `CREATE [UNIQUE] INDEX IF NOT EXISTS` | `communities`, `community_categories`, `community_channels`, `community_roles`, `community_members`, `community_member_roles` | **Zero.** Apenas FKs referenciando `users(id)` (`ON DELETE RESTRICT`, `ON DELETE CASCADE`, `ON DELETE SET NULL`). |
| `nexus-server/migrations/20261112000008_channels_permissions_and_messages.sql` | Apenas `CREATE TABLE IF NOT EXISTS` e `CREATE [UNIQUE] INDEX IF NOT EXISTS` | `channel_permission_overwrites`, `channel_messages`, `channel_read_states` | **Zero.** Apenas FKs referenciando `users(id)` e as novas tabelas de comunidades. |
| `nexus-server/migrations/20261112000009_community_invites_moderation_audit.sql` | Apenas `CREATE TABLE IF NOT EXISTS` e `CREATE INDEX IF NOT EXISTS` | `community_invites`, `community_bans`, `community_member_mutes`, `community_audit_logs` | **Zero.** Apenas FKs referenciando `users(id)` e as novas tabelas de comunidades. |

As tabelas preexistentes da `v0.2.5` (`users`, `user_credentials`, `user_profiles`, `sessions`, `user_oauth_accounts`, `friendships`, `friend_requests`, `user_blocks`, `user_presence_preferences`, `direct_conversations`, `direct_messages`, `direct_message_receipts`, `direct_conversation_states`, `password_reset_tokens`) permanecem intactas.

### 1.2 Endpoints REST da `v0.2.5` preservados

Em `nexus-server/src/routes/mod.rs`, todos os namespaces e rotas utilizados por clientes `v0.2.5` permanecem montados nos mesmos caminhos e protegidos pelos mesmos middlewares:

- **Sistema e desafio:** `GET /health`, `GET /reset-password`, `POST /v1/system/challenge`, `POST /system/challenge`.
- **Autenticação (`/v1/auth`):** `/register`, `/login`, `/google`, `/logout`, `/refresh`, `/google/link`, `/google`, `/password/bridge`, `/password/forgot`, `/password/verify`, `/password/reset`.
- **Usuários (`/v1/users`):** `/me`, `/me/presence`, `/search`, `/:id/block`.
- **Amigos (`/v1/friends`):** `/`, `/requests`, `/requests/:id/accept`, `/requests/:id/reject`, `/requests/:id/decline`, `/requests/:id`, `/:friend_id`.
- **Mensagens diretas (`/v1/dm`):** `/conversations`, `/conversations/:id/messages`, `/conversations/:id/read`, `/conversations/:id/delivered`, `/messages/:id`.
- **WebRTC ICE (`/v1/webrtc/ice-servers`):** `handlers::webrtc::get_ice_servers` (`nexus-server/src/handlers/webrtc.rs`) mantém o mesmo contrato `IceServersResponse { ice_servers, ttl_seconds }` com servidores STUN padrão e credenciais TURN efêmeras HMAC-SHA1.
- **Gateway WS:** `/v1/gateway`, `/v1/ws`, `/ws` e `POST /v1/gateway/ticket`.

As novas rotas de comunidades e convites foram adicionadas exclusivamente sob `/v1/communities` e `/v1/invites`, sem colisão ou alteração de rotas existentes.

### 1.3 Frames WebSocket da `v0.2.5` e chamadas 1:1 sem `stream_kind`

Em `nexus-server/src/models/mod.rs` e `nexus-server/src/handlers/ws.rs`:

- O handshake de autenticação aceita `Authorization: Bearer <token>` ou o primeiro frame `{"op": "authenticate", "token": ..., "ticket": ...}` dentro de `GATEWAY_AUTH_TIMEOUT_SECS = 5`.
- Os frames `set_presence`, `dm.delivery_ack`, `dm.read_ack`, `ping`, `call.invite`, `call.accept`, `call.reject`, `call.cancel`, `call.end` e `call.mute` mantêm exatamente os mesmos campos obrigatórios.
- Nos frames de sinalização WebRTC 1:1 (`call.webrtc.offer`, `call.webrtc.answer`, `call.webrtc.ice_candidate`), o campo `stream_kind` é anotado com:
  ```rust
  #[serde(default)]
  stream_kind: Option<String>,
  ```
- Quando um cliente `v0.2.5` envia `call.webrtc.offer`, `call.webrtc.answer` ou `call.webrtc.ice_candidate` **sem** `stream_kind`, o servidor desserializa `stream_kind` como `None`.
- No encaminhamento (`relay_sdp_with_stream_kind` e `relay_ice_with_stream_kind` em `nexus-server/src/services/calls.rs`), o campo `"stream_kind"` só é inserido no payload JSON de saída quando `Some(kind)` está presente. Para chamadas `v0.2.5` (`None`), o JSON recebido pelo peer é idêntico ao formato da `v0.2.5` (comportamento também coberto pelo teste unitário `test_webrtc_signaling_stream_kind_backwards_compat_and_parsing` em `nexus-server/src/models/mod.rs`).

## 2. Preservação na Atualização `v0.2.5 Stable -> v0.4.0 Stable`

O cliente desktop mantém o mesmo identificador de pacote (`"identifier": "com.nexus.desktop"`, `"productName": "nexus"` em `src-tauri/tauri.conf.json`), garantindo continuidade de diretórios de dados e credenciais no Windows:

1. **Banco SQLite local (`nexus.db`):**
   - Localizado em `app_data_dir` (`src-tauri/src/db.rs`).
   - Inicializado com migrações idempotentes (`_migrations`, `CREATE TABLE IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN` quando necessário), preservando conversas, mensagens, `conversation_state` (última lida e rascunhos), `cache_metadata` e `pending_messages` isolados por `account_id`.
2. **Tokens de sessão:**
   - Armazenados no gerenciador de credenciais do sistema operacional via `keyring::Entry` (`src-tauri/src/auth.rs`, chave `"session_token"` em builds de produção).
   - A atualização in-place pelo updater ou instalador NSIS não apaga entradas do Windows Credential Manager, preservando a sessão autenticada.
3. **Preferências de áudio, vídeo e tema:**
   - Persistidas em `nexus_settings.json` (Tauri Store em `app_data_dir`) via `SettingsRepository` (`src/repositories/SettingsRepository.ts`) — incluindo `theme`, `inputDevice`, `outputDevice`, `inputSensitivity`, `outputVolume`, `noiseSuppression`, `echoCancellation`, `autoGainControl`, `screenShareQuality`, `participantVolumes`, `callStageSplitRatio`, `voiceAutoSensitivity`, `voiceHangoverMs`, `voiceSoftGate` — e em chaves de `localStorage` (`nexus_theme`, etc.) dentro do diretório de dados do WebView2.
   - Nenhum desses armazenamentos é limpo pelo instalador NSIS (`src-tauri/nsis/hooks.nsh` apenas registra/remove o protocolo `nexus://`).
4. **Canal de atualização (`stable` vs `beta`):**
   - Persistido em `nexus_settings.json` (`app_update_channel`) e em `localStorage` (`nexus_app_update_channel`).
   - No pré-login, `PreloginUpdaterService` (`src/services/PreloginUpdaterService.ts`) lê o canal persistido antes de consultar o backend Rust (`updater_check_prelogin`).
   - Como `0.4.0` é maior que `0.2.5` em precedência SemVer 2.0.0 e não possui sufixo prerelease, clientes `v0.2.5` no canal `stable` detectarão a `v0.4.0` apenas quando ela for publicada oficialmente no canal `stable` (`latest.json`), mantendo o canal `stable` preservado após o upgrade.

## 3. Plano de Backup Pré-Deploy AWS

Como `nexus-server/src/main.rs` executa `sqlx::migrate!("./migrations").run(&pool).await` automaticamente na inicialização do servidor, **todo backup deve ser concluído e validado antes de iniciar o binário `v0.4.0`**.

### 3.1 Backup do PostgreSQL

1. Capturar dump lógico consistente antes de parar ou atualizar o serviço:
   ```bash
   TS=$(date -u +%Y%m%dT%H%M%SZ)
   BACKUP_DIR="/var/backups/nexus/${TS}"
   mkdir -p "${BACKUP_DIR}"
   pg_dump "$DATABASE_URL" --format=custom --no-owner --no-privileges --file="${BACKUP_DIR}/nexus_pre_v040_${TS}.dump"
   sha256sum "${BACKUP_DIR}/nexus_pre_v040_${TS}.dump" > "${BACKUP_DIR}/nexus_pre_v040_${TS}.dump.sha256"
   ```
2. Validar integridade do arquivo de backup antes de prosseguir:
   ```bash
   sha256sum -c "${BACKUP_DIR}/nexus_pre_v040_${TS}.dump.sha256"
   pg_restore --list "${BACKUP_DIR}/nexus_pre_v040_${TS}.dump" > "${BACKUP_DIR}/pg_restore_toc.txt"
   ```
3. Registrar snapshot basal (contagem de linhas das tabelas críticas `users`, `sessions`, `friendships`, `direct_messages` e conteúdo de `_sqlx_migrations`) e, se em EC2/RDS, criar snapshot EBS/RDS correspondente antes do cutover.

### 3.2 Backup do binário e configuração `nexus-server` v0.2.5

1. Copiar o binário em produção, unit file (se systemd) e variáveis de ambiente (sem expor segredos em logs):
   ```bash
   cp -a /usr/local/bin/nexus-server "${BACKUP_DIR}/nexus-server.v0.2.5.bin"
   sha256sum "${BACKUP_DIR}/nexus-server.v0.2.5.bin" > "${BACKUP_DIR}/nexus-server.v0.2.5.bin.sha256"
   cp -a /etc/systemd/system/nexus-server.service "${BACKUP_DIR}/nexus-server.service.bak" 2>/dev/null || true
   ```
2. Confirmar que o binário de backup existe e é executável (`chmod +x "${BACKUP_DIR}/nexus-server.v0.2.5.bin"`).

## 4. Procedimento de Rollback Seguro com Zero Perda de Dados

Em caso de necessidade de rollback após o deploy do `nexus-server` `v0.4.0`, **NÃO modifique `_sqlx_migrations`, NÃO delete registros do banco e NÃO exclua tabelas**.

### 4.1 Fundamento Técnico: Resolução do `VersionMissing` sem exclusão de dados

Em `nexus-server/src/main.rs:30`, o servidor executa:
```rust
sqlx::migrate!("./migrations").run(&pool).await?;
```

- **Comportamento nativo do SQLx 0.8:** O macro `sqlx::migrate!` embute as migrações em tempo de compilação. Durante o `.run(&pool).await`, o validador compara as versões registradas na tabela `_sqlx_migrations` com a lista conhecida no binário. Se o banco já recebeu as migrações da `v0.4.0` (`20261112000007..009`), um binário `v0.2.5` padrão falhará na inicialização com:
  ```text
  Error: VersionMissing(20261112000007)
  ```
- **A abordagem incorreta (rejeitada):** Deletar registros de `_sqlx_migrations` e executar `DROP TABLE` nas tabelas de comunidades destrói irreversivelmente todas as comunidades, canais, cargos, convites e mensagens criados durante o período em que a `v0.4.0` esteve ativa.
- **A abordagem correta e segura (Zero Data Loss):** Compilar um **binário de rollback baseado na `v0.2.5`** que reconhece as migrações `007..009`. Como as migrações `007..009` são estritamente aditivas (`CREATE TABLE IF NOT EXISTS`), incluir as migrações `20261112000007..009` na árvore de compilação da `v0.2.5` (ou utilizar `Migrator::set_ignore_missing(true)`) faz com que o validador do SQLx encontre todos os checksums idênticos e considere o esquema 100% atualizado.
- O binário executa o código estável da `v0.2.5` (atendendo autenticação, amigos, mensagens diretas e chamadas 1:1), enquanto as tabelas e dados de comunidades permanecem 100% íntegros e preservados no PostgreSQL.

### 4.2 Construção Prévia do Binário de Rollback (`v0.2.5-rollback`)

O binário de rollback deve ser construído e arquivado junto com os artefatos de deploy antes do cutover da `v0.4.0`:

```bash
# 1. Criar worktree temporária a partir da release estável v0.2.5
git worktree add --detach /tmp/nexus_wt_025 release/v0.2.5-stable

# 2. Copiar exclusivamente as migrações aditivas da v0.4.0 para a árvore de migrações
cp nexus-server/migrations/20261112000007_communities_core.sql /tmp/nexus_wt_025/nexus-server/migrations/
cp nexus-server/migrations/20261112000008_channels_permissions_and_messages.sql /tmp/nexus_wt_025/nexus-server/migrations/
cp nexus-server/migrations/20261112000009_community_invites_moderation_audit.sql /tmp/nexus_wt_025/nexus-server/migrations/

# 3. Compilar o binário de rollback estável (código v0.2.5 + migrações 001..009 reconhecidas)
cargo build --release --manifest-path /tmp/nexus_wt_025/nexus-server/Cargo.toml
cp /tmp/nexus_wt_025/nexus-server/target/release/nexus-server "${BACKUP_DIR}/nexus-server.v0.2.5-rollback.bin"
sha256sum "${BACKUP_DIR}/nexus-server.v0.2.5-rollback.bin" > "${BACKUP_DIR}/nexus-server.v0.2.5-rollback.bin.sha256"

# 4. Limpar a worktree temporária
git worktree remove --force /tmp/nexus_wt_025
```

### 4.3 Procedimento Operacional de Rollback na Produção (AWS)

Caso ocorra anomalia na `v0.4.0`:

1. **Parar o serviço `v0.4.0`:**
   ```bash
   sudo systemctl stop nexus-server
   ```

2. **Instalar o binário de rollback validado:**
   ```bash
   sha256sum -c "${BACKUP_DIR}/nexus-server.v0.2.5-rollback.bin.sha256"
   sudo install -m 0755 "${BACKUP_DIR}/nexus-server.v0.2.5-rollback.bin" /usr/local/bin/nexus-server
   ```

3. **Iniciar o serviço `nexus-server`:**
   ```bash
   sudo systemctl start nexus-server
   ```

4. **Validar a saúde do serviço pós-rollback:**
   ```bash
   curl -fsS http://127.0.0.1:8080/health
   ```
   - O servidor inicia sem erro de `VersionMissing`.
   - Rotas de login (`/v1/auth/login`), mensageria direta (`/v1/dm/*`) e chamadas funcionam normalmente.

### 4.4 Garantia de Integridade e Retomada (`v0.4.0+`)

- **Estado do banco de dados pós-rollback:**
  - `_sqlx_migrations`: Permanece intacto com todas as entradas `1..4`, `20261111000001` e `20261112000007..009`.
  - Dados de usuários e DMs: Intactos e operantes.
  - Dados de comunidades: `communities`, `community_channels`, `community_roles`, `community_invites` e `channel_messages` permanecem 100% preservados na íntegra.
- **Quando o hotfix `v0.4.0-nightly.2` (ou versão corrigida) for liberado:**
  - Basta instalar o novo binário e reiniciar o serviço (`sudo systemctl restart nexus-server`).
  - O novo servidor reconhecerá as tabelas já existentes e continuará a operação imediatamente com todos os dados pré-existentes e novos totalmente íntegros.

## 5. Estratégia Nightly -> Homologação -> Stable

A promoção entre canais segue separação estrita sem auto-promoção:

1. **Canal Nightly (`beta`):**
   - Gerado exclusivamente via `.github/workflows/nightly.yml` com versão prerelease (ex.: `0.4.0-nightly.1`) e publicado com o manifesto `latest-nightly.json`.
   - Apenas clientes configurados no canal `beta` (`latest-nightly.json`) recebem atualizações Nightly.
   - Clientes `v0.2.5` no canal `stable` consultam `latest.json` e possuem guarda dupla no cliente (`PreloginUpdaterService.ts`: bloqueio explícito quando `channel === 'stable' && isPrereleaseVersion(checkResult.version)`), garantindo que nunca recebam builds Nightly.
2. **Homologação:**
   - Validação funcional e de compatibilidade em ambiente isolado (`.github/workflows/homologation.yml` e testes de regressão `v0.2.5` <-> `v0.4.0` para auth, DM, amigos, chamadas 1:1 e comunidades) antes de qualquer decisão de promoção.
3. **Canal Stable (`stable`):**
   - Gerado exclusivamente via `.github/workflows/stable.yml`, que exige versão SemVer `X.Y.Z` sem sufixo prerelease (`^[0-9]+\.[0-9]+\.[0-9]+$`), sincronização dos metadados de versão e disparo manual após **autorização explícita do usuário**.
   - **Proibido** promover Nightly automaticamente para Stable ou alterar o canal Stable (`latest.json`) antes da autorização formal.
